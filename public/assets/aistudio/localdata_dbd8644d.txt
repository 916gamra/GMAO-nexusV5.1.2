**HEAD:** `9cd9856` — المستودع حي ومتقدم عن مراجعة 5.1.2 الأولى.

## 1) هل ميزات Excel والصيغ «ضاعت»؟

**لا — لم تُمسح.** ما زالت موجودة بوضوح:

| المكوّن | الحالة |
|---------|--------|
| `exceljs` | ✅ في الاعتمادات |
| `hyperformula` | ✅ محرك صيغ |
| `excelEngineService` / `formulaEngine` / `ExcelFormulaEngine` | ✅ |
| `typeAExcelBridge` + قوالب الاستيراد متعددة الأوراق | ✅ |
| `PdrCatalogExcelModal` / تصدير-استيراد كتالوج | ✅ |
| `EXCEL_FORMULAS.md` (معادلات Stock / Mouvements…) | ✅ |
| حزمة npm `xlsx` القديمة | أُزيلت عمداً (أمن) واستُبدلت بمسار محصّن + exceljs |

ما تغيّر فلسفياً (مهم):

- **Type A** = ملفات منظمة للاستيراد الآمن (حزم + Excel بقائمة `README_TYPE_A`).  
- **Type B** = تصدير تشغيلي للقراءة الخارجية (ليس لإعادة حقن عشوائية تكسر SSOT).

إذن قدرة «قراءة Excel + صيغ» **حية**؛ ما رُفض هو استيراد أي ملف Excel عشوائي كأنه قاعدة كاملة دون عقد.

## 2) التخزين اليوم (باختصار)

```text
ذاكرة RAM (العمل)
    ↕
IndexedDB — بدأ يصبح أساس المجموعات الثقيلة (Batch 5 موجود في الكود والاختبارات)
    ↕
localStorage — إعدادات ومفاتيح خفيفة + توافق قديم
    +
نسخ احتياطي JSON (AutoBackupService / اختيار ملف حفظ)
    +
خادم LAN اختياري: gmao_state.json على الجهاز المضيف
```

لستم أمام «ملف واحد مشفّر كهاكر». التشفير إن وُجد فهو لجلسات/أسرار، لا كشكل وحيد لكل بيانات المصنع.

## 3) ماذا تريدون أنتم؟ وما النظام المناسب؟

طلبتم:

- ليس ملفاً واحداً ضخماً مشفّراً  
- قاعدة **ملفات** مفهومة  
- Excel متعدد الصفحات إن أمكن  
- يناسب جهاز واحد / بضع أجهزة + مجلد شبكة لاحقاً  

### التوصية: **مجلد بيانات (Data Folder) وليس ملف وحش واحد**

```text
GMAO_Data/                    ← مجلد تختاره من الإعدادات (محلي أو \\server\gmao\)
  manifest.json               ← إصدار التطبيق، تاريخ الحفظ، قائمة الملفات
  catalog/                    ← مراجع بطيئة التغيّر
    zones.json
    machines.json
    personnel.json
    pdr_items.json
    ...
  operational/                ← حركة يومية
    mouvements.json
    corrective.json
    preventive_executions.json
    ...
  exports/                    ← اختياري: مرايا Excel للقراءة البشرية
    Stock_Catalogue.xlsx      ← عدة أوراق (Groups / Types / Items)
    Parc_Machines.xlsx
```

| الخيار | متى؟ |
|--------|------|
| **JSON لكل مجموعة** داخل مجلد | الأفضل كـ SSOT تقني: ذري نسبياً، واضح، يُنسَخ على الشبكة، بدون صيغ تُكسر عند الحفظ |
| **Excel متعدد الأوراق** | ممتاز للكتالوج والاستيراد/التصدير البشري (Type A) وللتقارير — **مرآة أو بوابة إدخال**، لا محرك كتابة حي لكل ضغطة في الورشة |
| **ملف JSON واحد ضخم** | مقبول كنسخة احتياطية فقط (`backup-2026-11-23.json`) — ليس كقاعدة يومية |
| **ملف مشفّر واحد** | غير مناسب لعملكم اليومي ولا لوضع الملف على مشاركة ويندوز ببساطة |

**لماذا ليس Excel هو المحرك الحي الوحيد؟**  
الصيغ (SUMIFS…) رائعة في القالب البشري، لكن الكتابة المتزامنة من التطبيق + فتح الملف في Excel من شخص آخر = تعارض وفساد. النموذج الناضج:

```text
التطبيق يعمل على JSON (مجلد) + IDB محلياً
Excel = استيراد كتالوج / تصدير تقرير / Twin للمعادلات
وليس = قاعدة تُحفظ بعد كل صرف قطعة
```

هذا يحترم اختياركم السابق لـ Excel والصيغ **دون** أن يجعل المصنع يعتمد على ملف `.xlsx` مفتوح على الشبكة كقاعدة حية.

## 5) خطة مرحلية مقترحة (أنا أختار النظام)

### المرحلة L1 — مجلد بيانات JSON (أساس)

1. من الإعدادات: **اختيار مجلد** (File System Access API حيث يتوفر) أو تصدير/استيراد حزمة مجلد (zip من JSON إن لزم على متصفحات ضعيفة).  
2. `manifest.json` + ملف JSON لكل مجموعة منطقية (نفس تقسيم `STORAGE_KEYS` / الحزم Type A).  
3. عند الحفظ: كتابة ذرية (`*.tmp` ثم استبدال) لكل ملف تغيّر.  
4. المتصفح يبقى يعمل بـ IDB/RAM؛ المجلد = **مرآة/نسخة معتمدة** يفتحها المستخدم من المستكشف وينسخها على السيرفر.

### المرحلة L2 — Excel كطبقة بشرية (موجودة جزئياً)

- الإبقاء على Type A متعدد الأوراق للكتالوج.  
- تصدير دوري لـ `exports/*.xlsx` للقراءة في Excel (معادلاتكم موثّقة في `EXCEL_FORMULAS.md`).  
- لا جعل `.xlsx` مصدر الحقيقة الوحيد للكتابة الحية.

### المرحلة L3 — مشاركة شبكة

- نفس المجلد على `\\serveur\gmao\GMAO_Data`.  
- في البداية: **محطة كتابة رئيسية واحدة** أو حفظ يدوي «دفع إلى المجلد».  
- قفل متقدم لاحقاً إن احتجتم جهازين يكتبان معاً.

# نقاش عميق: تخزين مجلد أصلي على Windows — لا متصفح كهدف

ما تطرحونه ليس «تحسين PWA»، بل **إعادة تعريف مصدر الحقيقة**:  
التطبيق = عميل سطح مكتب أصلي؛ **المجلد الذي يختاره المستخدم = قاعدة المصنع**.

هذا متسق مع رفضكم للمتصفح كبيئة إنتاج، ومع 1–4 أجهزة وLAN الشركة.

---

## 1) المتصفح مقابل Windows أصلي

| في المتصفح | على Windows أصلي (Electron / Tauri / مشابه) |
|------------|-----------------------------------------------|
| File System Access محدود، أذونات هشة | مسار مجلد دائم، صلاحيات عادية كأي برنامج |
| localStorage / IDB سقف وقيود | المجلد على القرص هو الأساس |
| مشاركة الشبكة متعبة من الواجهة | Windows يشارك المجلد؛ التطبيق يرى مساراً فقط |

**خلاصة:** لا نضيع جهداً كبيراً الآن على التفافات المتصفح من أجل «مجلد حي».  
نصمّم **عقد المجلد + المحرك** بحيث يعمل اليوم حيث أمكن (تجريبي)، ويصبح طبيعياً 100% تحت غلاف Windows لاحقاً.  
أي كود يفترض أن «الحقيقة في localStorage فقط» يُعاد توجيهه تدريجياً:  
**RAM للجلسة ← المجلد للبقاء ← (اختياري) كاش محلي للسرعة.**

---

## 2) ربط نظام الاستيراد/التصدير بنظام المجلد

عندكم أصلاً طبقات ناضجة:

- **Type A** = حزم منظمة / Excel بعقد واضح للاستيراد  
- **قوالب رسمية** للتصدير  
- **JSON backup** تشغيلي  

المجلد المحلي يجب أن يكون **نفس الفلسفة، لا نظاماً ثالثاً غريباً**:

```text
نفس الشكل المنطقي للحزم
    ↓
ملفات داخل المجلد = «الحزمة الدائمة المفتوحة»
    ↓
الاستيراد Type A = صبّ دفعة داخل المجلد (دمج/استبدال حسب السياسة)
التصدير Type A / Excel = قراءة من المجلد وتوليد ملف للمستخدم الخارجي
التطبيق الحي = يقرأ/يكتب نفس الملفات (أو طبقة عليها)
```

| العملية | علاقتها بالمجلد |
|---------|------------------|
| حقن بنية فارغة | إنشاء شجرة `catalog/` + `operational/` + `manifest.json` كقالب Type A فارغ |
| استيراد Type A | ملء/دمج ملفات المجلد (لا localStorage كوجهة نهائية) |
| تعديل يدوي خارج التطبيق | فتح `machines.json` أو Excel كتالوج → عند التشغيل التالي يُحمَّل بعد تحقق |
| تصدير | قراءة المجلد → ملف للمشاركة أو الأرشفة |

**نعم هناك ترابط قوي مطلوب:**  
قوالب الاستيراد ليست ميزة جانبية؛ هي **شكل البيانات الرسمي** لملفات المجلد.  
ما ناقص اليوم غالباً: جعل المجلد هو **المسار الافتراضي للقراءة/الكتابة**، لا مجرد «استورد مرة وانسَ الملف».

---

## 3) محرك المجلد الذكي — قواعد سليمة

### أ) مجلد فارغ تماماً

```text
→ إنشاء البنية كاملة (قالب فارغ)
→ manifest: version, createdAt, appVersion, schemaVersion
→ جاهز للكتابة من التطبيق أو للملء اليدوي بحذر
```

### ب) مجلد فيه البنية كاملة وسليمة

```text
→ لا إعادة حقن
→ فتح عادي (استخدام البيانات الموجودة)
```

### ج) مجلد فيه بعض الملفات / بنية ناقصة

```text
→ لا حذف صامت
→ تقرير: موجود / ناقص / زائد / تالف
→ خيارات صريحة:
   1) استكمال الناقص فقط (ملفات فارغة [] أو {}) — إصلاح بنية
   2) استخدام الموجود كما هو مع تحذير الحقول الناقصة
   3) إلغاء واختيار مجلد آخر
→ خيار «حذف وإعادة قالب فارغ» فقط بتأكيد مزدوج إذا كانت هناك بيانات
```

### د) مجلد غير فارغ وبدون توقيع GMAO (ملفات عشوائية)

```text
→ رفض أو «إنشاء مجلد فرعي GMAO_Data داخلها» — أفضل من خلط صور المستخدم مع JSON المصنع
```

هذا أقرب لمنطق Nexus «اكتشف النواقص» مما لـ«امسح كل شيء».

---

## 4) جهازان + مشاركة مجلد Windows — هل تغني عن «ملف سيرفر معقّد»؟

**نعم كفكرة بنية تحتية بسيطة:**

```text
PC1: يختار D:\GMAO_Data → يحقن البنية → يعمل
Windows: مشاركة المجلد على LAN
PC2: يختار \\PC1\GMAO_Data → المحرك يرى البنية → «استخدام الموجود؟» → نعم
```

لا حاجة لـ«منتج سحابي».  
ما يبقى ضرورياً:

1. **من يكتب ومتى** — جهازان يكتبان نفس `mouvements.json` في نفس اللحظة بدون تنسيق = خطر.  
2. عندكم بذور **LAN sync / host** — دورها يصبح:  
   - قفل منطقي أو طابور كتابة، أو  
   - محطة «مضيف» تملك الكتابة الثقيلة والأخرى تقرأ أكثر، أو  
   - ملفات عمليات صغيرة + دمج دوري  

لا تستبدلوا محرك المجلد بـ LAN معقّد؛ **المجلد هو القرص، وLAN يمنع التلف.**

لجهاز واحد 90% من الوقت: المشاركة نادرة؛ التحقق عند الفتح يكفي.

---

## 5) التحقق عند كل فتح — دون إرهاق

التحقق الكامل لكل الملفات في كل إطلاق = بطيء ومزعج إن كبر الحجم.

نموذج أنضج:

```text
عند الفتح:
  1) قراءة manifest فقط (سريع)
  2) فحص وجود الملفات الإلزامية (أسماء + حجم منطقي) — قائمة قصيرة
  3) إن schemaVersion مطابق و«آخر فحص سليم» حديث → دخول عادي
  4) فحص عميق (JSON parse لكل ملف، حقول إلزامية) فقط إذا:
       - تغيّر مسار المجلد
       - تغيّر schemaVersion التطبيق
       - فشل قراءة ملف أثناء العمل
       - المستخدم طلب «فحص سلامة البيانات»
       - أو مرّت مدة / علم dirty من خارج التطبيق (اختياري: hash في manifest)
```

عند الخطأ:

- رسالة واحدة واضحة + **ضبط المجلد** / **استكمال البنية** / **فتح تقرير النواقص**  
- لا معالج من 12 شاشة في كل صباح.

---

## 6) التعديل اليدوي من خارج التطبيق

ممكن ومفيد للكتالوج (zones، آلات، قوائم PDR) إذا:

- التزم الملف بـ **schema** بسيط (نفس حقول Type A)  
- عند التحميل: رفض الملف التالف، لا دمج أعمى  
- الحركات اليومية (`mouvements`, إغلاقات BT) يُفضّل ألا تُعدَّل يدوياً إلا للصيانة المتقدمة  

Excel متعدد الأوراق: ممتاز كـ **واجهة بشرية للكتالوج**؛  
المجلد يبقى JSON (أو JSON + Excel مرآة) حتى لا تُكسر الصيغ الحية بالكتابة الثنائية من التطبيق.

---

## 7) ماذا عن جذور Nexus / إصلاح الحقول؟

المنطق الذي بدأتموه (اكتشاف فراغات، طلب إكمال) **يناسب مرحلة «بعد ربط المجلد»**:

- عند التحميل: عناصر `needs_classification` أو حقول إلزامية ناقصة → قائمة في Nexus أو شارة  
- لا يمنع التشغيل إن كان الوضع الميداني يسمح بالنواقص  
- يمنع فقط ما يكسر المخزون أو السلامة (مرجع حركة بلا صنف، إلخ) حسب قواعد صارمة قليلة  

يُستحسن جرد سريع في الكود لاحقاً: ماذا بقي من فحوصات Nexus قابلة للربط بـ`manifest`/تحميل المجلد — دون إعادة بناء من صفر إن وُجدت جذور.

---

## 8) ترتيب عقلي للتنفيذ (بدون تبسيط مخل)

```text
الآن (عقد)
  • توثيق: المجلد = SSOT على سطح المكتب
  • شكل الشجرة + manifest + schemaVersion
  • ربط الشكل بحزم Type A الموجودة (نفس الأسماء/الحقول قدر الإمكان)

ثم محرك
  • فارغ → قالب
  • كامل → استخدام
  • ناقص → استكمال / تقرير
  • غريب → رفض أو مجلد فرعي

ثم جلسة التشغيل
  • تحقق خفيف عند الفتح + عميق عند الحاجة
  • كتابة ذرية لكل ملف تغيّر

ثم جهازان
  • مشاركة Windows + «استخدام البنية الموجودة»
  • تشديد LAN فقط لمنع كتابة متزامنة مدمّرة

الغلاف Windows الأصلي
  • يسهّل المسار الدائم والصلاحيات؛ العقد نفسه لا يعتمد على «حيلة متصفح»
```

---

## 9) خلاصة النقاش

- رفض المتصفح كهدف إنتاج → **صحيح** لتوجيه التخزين نحو مجلد حقيقي.  
- بنية ملفات + قالب عند الاختيار + تعديل خارجي حذر → **مترابطة مع Type A** ويجب أن تُبنى عليه لا بجانبه.  
- محرك فارغ / موجود / ناقص → **المنطق الصحيح**؛ الإصلاح استكمال لا مسح صامت.  
- جهازان عبر مشاركة مجلد Windows → **بديل بسيط وذكي** لـ«سيرفر ملف معقّد»، مع بقاء حاجة لتنسيق كتابة.  
- تحقق كل فتح → **خفيف دائماً، عميق عند الشك** — لا إرهاق ولا إهمال.

إذا وافقتم، الخطوة التالية للنقاش أو للموجّه:  
**تثبيت شجرة المجلد + محتوى `manifest.json` + قائمة الملفات الإلزامية مقابل `STORAGE_KEYS`/حزم Type A** — قبل أي سطر يلمس الكتابة الحية للمخزون.
# نتيجة المراجعة — هل الريبو متوافق؟ وهل يكسر الوكيل التطبيق؟

## التوافق مع الطموح

| الطبقة | في الريبو الآن | علاقتها بالمجلد |
|--------|----------------|------------------|
| حزم Type A (7) + قوالب JSON/Excel | ✅ قوية وموثّقة | **شكل البيانات الرسمي** للمجلد |
| `UnifiedImportPipeline` / `typeAExcelBridge` | ✅ | الاستيراد يصبّ في نفس الحقول لاحقاً |
| `STORAGE_KEYS` + DataGateway | ✅ SSOT الحالي للمتجر | يبقى كما هو في هذه الدفعة |
| IDB / localStorage / Backup JSON | ✅ | لا يُقطع |
| اختيار **مجلد دائم** كـ SSOT حي | ❌ غير موجود كمحرك | ما نبدأ ببنائه |
| غلاف Windows أصلي | ❌ لاحقاً | العقد يُصمَّم ليناسب المسار لاحقاً |

**الخلاصة:** الريبو **متوافق كعقد بيانات** (Type A + مفاتيح + بوابة).  
**غير جاهز** لأن يكون المجلد هو مصدر الحقيقة الحي لكل ضغطة — وهذا متعمّد في الموجّه: **مرحلة عقد + محرك بنية فقط، بلا تحويل الكتابة الحية.**

بهذا لا يكسر الوكيل المخزون ولا الوقائي ولا Pipeline إن التزم النطاق.
